# Auto-rehydrate on session start — design

**Status:** Approved, ready for planning.
**Origin:** brainstorming session, 2026-08-12.

## Purpose

Today, updating the `aipe` binary (`aipe upgrade`, or accepting the
interactive update offer) only updates the binary itself. A workspace's
already-installed skills (coordinator flow-skills, per-repo persona skills,
toolbox) are static copies written at `aipe start`/`/hire-specialists` time
— upgrading the binary does not touch them. The PE currently has to
remember to also run `aipe rehydrate --workspace <dir>` after every upgrade,
for every workspace, or that workspace silently keeps running stale skills.

This closes the gap: whenever a `SessionStart` hook fires (workspace root or
a specialist repo — both fire the same hook since the repo-local session
context feature), it detects that the installed skills were generated by an
older binary version than the one currently running, and silently
re-syncs them before injecting awareness — no PE action required, and it
self-heals any workspace the next time a session opens there, regardless of
where or when the binary was upgraded.

## Non-goals

- Not stamping/rehydrating from `aipe start` or `aipe rehydrate`'s own CLI
  paths — the first session after an upgrade already triggers it, and
  rehydrate is cheap/idempotent when there's nothing to update.
- Not surfacing "skills were just updated" in the injected awareness text —
  this is silent automation, not a notification. Can be added later if
  wanted.
- Not tracking or rehydrating workspaces the PE hasn't opened a session in
  since the upgrade — out of scope; each workspace self-heals on its own
  next session, which is sufficient for the stated goal ("the user
  shouldn't have to worry about it").

## Design

**New file: `src/session-hook/auto-rehydrate.ts`**

```typescript
export interface RehydrateDeps {
  rehydratePersonas: (root: string) => Promise<unknown>;
  rehydrateToolbox: (root: string) => Promise<unknown>;
  rehydrateFlowSkills: (root: string) => Promise<unknown>;
}

export async function ensureRehydrated(
  root: string,
  currentVersion: string,
  deps?: RehydrateDeps,
): Promise<boolean>; // true iff a rehydrate actually ran
```

Reads `<root>/.aipe/toolchain.yaml` (`{ aipeVersion: string }`). If its
`aipeVersion` already equals `currentVersion`, returns `false` immediately
(no I/O beyond the one read — the common case on every normal session
start). Otherwise calls the three injected rehydrate functions (defaulting
to the real `rehydratePersonas`/`rehydrateToolbox`/`rehydrateFlowSkills`
from `src/rehydrate/*`, called directly — not through `aipe rehydrate`'s CLI
wrapper, so nothing prints to stdout and corrupts the hook's JSON output),
writes the new stamp, and returns `true`. Any error anywhere in this path is
caught and swallowed — a rehydrate failure degrades to "skills stay a bit
stale this session," never to "the hook crashes and no awareness is
injected at all."

**Wiring: `src/session-hook/read-state.ts`'s `runSessionContext`**

After resolving `fields` via `readState`, if `fields.root` is non-empty
(brain present, `.aipe/` found), call `ensureRehydrated(fields.root,
VERSION)` before proceeding to the existing coordinator/persona branching —
`VERSION` imported from `../cli` (an existing precedent: `src/update/cli.ts`
already imports `VERSION` from `../cli` despite the reverse import existing
too; both work because `VERSION` is only read inside function bodies,
called long after the module graph finishes initializing, never at either
module's top level).

## Testing

- `auto-rehydrate.ts`: pure-ish, tested with a temp `.aipe/toolchain.yaml`
  and fake `RehydrateDeps` (matching the `Inspector`/`Cloner` fake-dependency
  pattern already used elsewhere in this codebase) — asserts: matching
  stamp → deps not called, `false` returned; missing/mismatched stamp →
  deps called, new stamp written, `true` returned; a deps function that
  throws → swallowed, `false` returned, no crash.
- `read-state.ts`: extend `runSessionContext`'s existing test coverage (or
  the end-to-end `runSessionContext` integration test added by the
  repo-local-session-context feature) with one case confirming a stale
  stamp doesn't prevent the hook's JSON output from being emitted.
