# `aipe handoff` — design

**Status:** Approved, ready for planning.
**Origin:** brainstorming session, 2026-08-11.

## Purpose

A technical PE frequently needs to give a non-technical collaborator (e.g. a
UI/UX designer who "vibe codes") a working environment where *that person's*
Claude Code already knows which repositories exist, where they live, and how
they relate — without the designer ever having to answer technical questions
("where does this data come from", "which repo owns this API") or install
AIPe themselves.

`aipe handoff` generates a single, portable `CLAUDE.md` file that the PE
builds once (using AIPe, which they have installed and understand) and hands
to the designer. The designer drops it into an empty folder, opens Claude
Code there, and the harness has everything it needs: clone instructions,
where each repo lands, what each repo is for, and how they relate to each
other.

This reuses AIPe's existing cross-repo relationship discovery (`/relationship`)
but produces a lightweight, standalone artifact instead of a full publishable
workspace — no `.aipe/` state, no `brain.yaml`, no personas, no dispatch.

## Non-goals

- Not a replacement for `/context-brain` → `/make-workspace` → `/relationship`
  → `/hire-specialists`. That pipeline remains the way to build a real,
  ongoing multi-agent AIPe workspace. `aipe handoff` is a one-shot export for
  someone who will never run AIPe at all.
- Does not manage workspace state, phases, or personas.
- Does not require the recipient to have AIPe installed — the output is a
  plain markdown file any Claude Code (or compatible harness) session reads
  automatically.

## Architecture

New command in `src/handoff/`, following the repo's established skill + pure
deterministic CLI split (same pattern as `/relationship`, see
`docs/dossie/04-relationship.md` decision 5).

**Input:** a list of repos, each given as a remote URL and/or an already
cloned local path (mixed lists allowed) — via repeated `--repo <url-or-path>`
flags.

**Skill (`skills/handoff/SKILL.md`)** — orchestrates live, in the coordinator's
session:
1. For any repo given only as a URL, clone it (into `--workdir`, default a
   temp dir, or directly next to the output file).
2. Dispatch one `Agent()` per repo, schema-forced to the same relation
   contract `/relationship` already uses (`imports | published-by | consumes
   | exposed-by | shares-infra`), plus a purpose/stack summary for that repo
   (new fields — `/relationship`'s stack backfill is coupled to `brain.yaml`,
   which `handoff` does not have).
3. Save each agent's structured report to disk (same "stage via files"
   pattern as `/relationship`, for inspectability and fixture-testing).

**CLI (`src/handoff/`)** — deterministic, pure where possible:
- Reads the staged reports.
- Reuses `src/relationship/merge.ts` unchanged to consolidate raw relations
  into `MergedEdge[]`.
- A new `render.ts` renders the single `CLAUDE.md` output (`--out`, default
  `./CLAUDE.md`).

## `CLAUDE.md` output structure

Fixed template, produced by pure `render.ts` (nodes/edges/repos → markdown
string), so it is testable without live agents:

```markdown
# Context Handoff — <context name>

> Generated by `aipe handoff` on <date>. This file gives Claude (or any
> compatible harness) the full map of these repositories and how they relate
> — there is no need to ask the user about this.

## Setup

git clone git@github.com:org/repo-a.git
git clone git@github.com:org/repo-b.git

## Repositories

| Repo | Local path | Purpose | Stack |
|------|-----------|---------|-------|
| repo-a | ./repo-a | Payments API | Go |
| repo-b | ./repo-b | Frontend | React/TS |

## Relations

- **repo-b → repo-a**: consumes the payments REST API (`src/api/client.ts` → `/v1/payments`)
- **repo-a, repo-b**: share auth infra via Cognito

## Pending (only if some repo failed)

- repo-c: clone failed / no valid report — retry `aipe handoff --repo <url> --workdir <dir>`

<details>
<summary>Structured graph (for agents)</summary>

```yaml
nodes: [...]
edges: [...]
```

</details>
```

- Relations are rendered both as human-readable prose **and** as an embedded
  YAML block using the same `GraphNode`/`MergedEdge` shape `/relationship`
  already produces — inline instead of a separate `graph.yaml` file, so
  agents can parse it reliably and humans can read the same file directly.
- No workspace/persona/dispatch sections — only what the designer's harness
  needs to set up the environment and understand the architecture.

## Partial failure

If a repo fails to clone, or its agent never returns a valid report, the
command does not abort. `CLAUDE.md` is still generated for every repo that
succeeded, and a `## Pending` section lists what failed and how to retry —
same posture as `/make-workspace` and `/relationship`.

Report validation reuses `/relationship`'s closed-enum validation
(`RelationType`): an invalid report is rejected in full, not partially
merged, so the embedded graph never contains out-of-contract data.

## Testing

- `render.ts`: pure, tested with fixture nodes/edges/repos → expected
  markdown string — mirrors `src/relationship/__tests__/render.test.ts`.
- Report validation and `merge.ts`: reused as-is from `src/relationship`,
  already covered.
- Clone orchestration: reuses/tests against the same logic already covered
  in `make-workspace`.
- Agent dispatch: exercised via the SKILL.md flow with simulated JSON
  reports on disk, same manual end-to-end strategy as `/relationship`
  (dossier 04, plan item 6) — no live agents needed for CLI-level tests.

## Open questions for planning

- Exact repo-declaration input format: flags only, or also a simple
  declarative file (reusing `context-brain`'s repo-list parsing) for large
  repo lists.
- Where cloned repos land by default when only URLs are given: next to
  `CLAUDE.md` (so the output folder is immediately usable) vs. a separate
  `--workdir`. Leaning toward "next to `CLAUDE.md`" since the whole point is
  a self-contained handoff folder — to be confirmed during planning.
